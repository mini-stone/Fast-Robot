1. Objective

The goal of Lab 12 is to implement a closed-loop controller that makes the robot balance on its rear wheels — a classic inverted pendulum (wheelie) stunt. The controller must stabilize the robot around the upright equilibrium point using onboard IMU data, with gains tuned through experimentation.

2. Approach & Design Choices

Method Selection

The lab offers two implementation paths: (1) start from the upright position and immediately stabilize, or (2) drive forward, brake sharply, and engage the controller mid-flip. Method 1 was chosen because it isolates the balancing control problem without coupling it to a velocity/brake maneuver, making parameter tuning more straightforward and the failure mode easier to diagnose.

PD vs. PID

A PD controller (no integral term) was used. Adding an integrator is typically counterproductive for an inverted pendulum: any sustained lean causes the integrator to wind up and drive the robot further off-balance before it can correct. The derivative term provides the necessary damping to prevent oscillation around the setpoint, which a pure P controller cannot achieve. Since the robot starts from a manually-placed upright position, steady-state error elimination (the usual role of the integral term) is not a priority.

3. Sensor & State Estimation

IMU & DMP

The ICM-20948 IMU's on-chip Digital Motion Processor (DMP) is used to compute a 6-axis Game Rotation Vector (quaternion) at the hardware level. Pitch angle is derived from the quaternion via: 

double tp1 = 2.0 * (qw * qx + qy * qz);
double tp2 = 1.0 - 2.0 * (qx * qx + qy * qy);
pitch_deg = (float)(atan2(tp1, tp2) * 180.0 / PI);

The DMP runs at its maximum ODR (register value 0), delivering quaternion updates faster than the main control loop can consume them. At each control cycle, the code drains the entire FIFO to obtain the latest available quaternion, minimising latency.

Is a Kalman Filter Needed?

For this application, no additional Kalman Filter is required. The DMP already fuses accelerometer and gyroscope data internally, producing a smooth, drift-corrected attitude estimate. The raw pitch readings used in the controller show noise well below 0.5°, which is smaller than the practical balance tolerance of the robot. The control loop runs at roughly 10 ms intervals (limited by DMP ODR and BLE overhead), which is fast enough for a robot with the inertia of the RC car. Adding a software Kalman Filter on top of the DMP output would introduce unnecessary latency.

4. Control Implementation

The pendulum controller runs inside update_pendulum(), called every iteration of the BLE-connected main loop. The core PD law is: 

float angle = pitch_deg - pend_pitch_offset;   // 0 = upright
float err   = angle - pend_setpoint;

float raw_deriv = (err - pend_prev_err) / dt;
pend_deriv_filtered = PEND_DERIV_ALPHA * raw_deriv
                    + (1.0f - PEND_DERIV_ALPHA) * pend_deriv_filtered;

float u_f = pend_kp * err + pend_kd * pend_deriv_filtered;
int   u   = (int)u_f;

Key implementation details:

  • Pitch offset calibration: Before running, GET_PITCH (BLE command 33) is used to read the raw pitch_deg while the robot is manually held upright. This value is stored as pend_pitch_offset, so angle = 0 corresponds exactly to the balanced position.
  • Derivative filter: A first-order low-pass filter (α = 0.1) smooths the derivative to reduce PWM chatter caused by quantisation noise in the pitch angle.
  • Minimum PWM: The output is clamped to [PEND_MIN_PWM, 255] = [85, 255] (preserving sign) so that the motor always overcomes static friction and responds immediately.
  • Safety cutoff: If |angle − setpoint| > 30° the controller stops the motors and sends PEND_STOPPED over BLE, preventing the robot from driving away after an unrecoverable fall.

5. Parameter Tuning

Three combinations of Kp and Kd were tested. In each trial the robot was placed upright by hand, START_PENDULUM was sent over BLE, and the robot ran until the safety cutoff triggered or the run was manually stopped. Logged data was retrieved with SEND_PENDULUM_DATA.

TrialKpKdObservation
12.51 Gains too low — robot corrects slowly, pitch drifts upward over time and eventually falls forward.
24.53 Best result — tight oscillation within ±5°, stable for the full run, motors respond quickly without chatter.
38.54 Gains too high — motor PWM saturates at ±255 almost every cycle, robot vibrates violently and falls within 1–2 seconds.

7. Results & Discussion

With the final gains Kp = 4.5, Kd = 3, the robot successfully balanced on its rear wheels for repeated runs. Key performance metrics from the logged data:

  • Steady-state pitch error: oscillates within approximately ±5° around the setpoint during stable balancing.
  • Control loop period: approximately 10–15 ms, consistent with the DMP FIFO update rate.
  • Motor output: typically ±85–120 PWM during steady balance, only reaching higher values during large perturbations.

The main challenge encountered was pitch offset calibration: if the robot is not held at exactly the same upright angle each time, the effective setpoint shifts and the controller fights a non-zero bias. This was mitigated by always running GET_PITCH immediately before each trial and updating pend_pitch_offset accordingly.

A secondary challenge was motor deadband: below ~85 PWM the motors do not move, creating a dead zone where the controller outputs a signal but produces no physical correction. The PEND_MIN_PWM = 85 constant addresses this by enforcing a minimum drive level whenever a non-zero output is commanded.

8. Conclusion

A PD inverted pendulum controller was successfully implemented on the Artemis-based RC car. Using the ICM-20948 DMP for low-latency pitch estimation, the robot can balance on its rear wheels for extended periods with final gains Kp = 4.5, Kd = 3. The iterative parameter tuning process — testing under-damped, well-tuned, and over-damped configurations — demonstrates clearly how each gain affects stability and response speed.
